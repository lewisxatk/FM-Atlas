# FM Atlas R4.3 — FM27 career import research & implementation contract

## Purpose
This document records the evidence-backed route for expanding the existing read-only live importer into a full career intelligence workspace. It distinguishes public FM27 reverse-engineering observations from fields already validated in the FM Atlas Windows build. A value is not considered production-ready merely because a public memory-layout repository lists an offset.

## FMRTE workflow and product model
FMRTE's current documentation describes a live workflow: open the career in Football Manager, use Load Game in FMRTE to read the running save, then navigate via the manager/club/favourites shortcut. Its search model separates players, coaches/staff and clubs; advanced player search includes age, nationality, ability, attributes, positions and contract criteria, while coach search includes coaching/scouting attributes and club search includes facilities, finances, debt and stadium details. FM Atlas should reproduce the useful workflow and categories with its own code and transparent evidence, not copy proprietary implementation.

Sources:

- https://docs.fmrte.com/scouting/search/
- https://www.fmrte.com/

## Career identity / My Club algorithm
1. Attach to the running FM process with query/read-only rights only.
2. Identify the loaded `game_plugin.dll`; record file version, module hash, image size and process path.
3. Select a layout profile by exact fingerprint. Unknown fingerprint = stop safely.
4. Read the staff array bounds and validate pointer ranges before dereferencing.
5. Identify the human-manager class by the build-specific vtable. Do not identify the manager by a hard-coded name or a Steam profile placeholder.
6. Exclude the account/Steam placeholder using validated structural evidence (the public notes describe an empty DOB and null nation/birthplace/contract pointers in their test build).
7. Decode manager name, staff UID, DOB, nationality and contract; compare each with visible in-game profile data.
8. Follow contract employer → team → club. Resolve that club pointer against the decoded club array, then verify its UID/name and at least one known player/team relationship.
9. Store a CareerIdentity snapshot with field-level provenance and confidence. Only then enable My Club.
10. If any required identity link is ambiguous, show “Career identity not verified” and keep My Club disabled; never guess based on the user's name or a likely club.

## All clubs and squad population
The existing live schema already has `LiveClubs`, `LiveTeams`, `LivePlayers`, `LiveStaff`, `LiveTeamLinks`, `LiveAffiliations`, `LiveCompetitions` and field-provenance tables. The current import payload, however, only commits clubs and players with a player-to-team object address and club UID. It does not yet decode team UIDs/names, senior/reserve/youth squad types, staff, competitions or affiliations.

Implementation order:
1. Decode every real club record; filter non-club placeholder classes by validated vtable/type evidence.
2. Decode team objects and their owning club; derive senior/reserve/youth squad classification only from verified team metadata or relationships.
3. Link every player to a team and club; retain unresolved team links separately rather than assigning the first team.
4. Decode staff array identities, role/job, nationality, contract and employer; map staff to club/team.
5. Add club profile fields (reputation, stadium, facilities, finance) individually with class gates, units and evidence.
6. Import affiliations, competitions and nations only when their arrays and links are validated.

## Scouting / search feature matrix

### Players
- Identity: full/common name, UID, DOB, age as of in-game date, nationality, birthplace, foot, height.
- Football: position/suitability, technical, mental, physical, goalkeeper attributes, preferred moves, personality, hidden attributes, CA/PA, reputation.
- Career: team, club, squad, competition, contract wage/expiry/status, transfer/loan flags, value/asking price, caps/goals, season stats.
- Recruitment: role suitability, positional need, filters, sortable/customizable columns, saved search profiles, comparisons, shortlists, export.

### Staff
- Identity and employer, role/job, nationality, DOB, contract.
- Coaching, mental, scouting, judging player ability/potential, tactical knowledge and other staff ratings.
- Filters by role, attribute bands, nationality, age and contract.

### Clubs
- Identity, nation, competition, teams/squads, player lists and staff.
- Finance, budgets, wage budget, debt, facilities, reputation, stadium, colours, affiliations and history where validated.

### UI
- Aurora Frost: white/ice-blue surfaces, navy typography, restrained blue selection, soft borders, rounded cards, generous spacing.
- Player search remains a three-column workspace: filters left, Wyscout-like configurable results grid centre, selected-player profile right.
- No player portraits or club logos required; use neutral initials/icons and a small deterministic colour strip only when a genuine club colour is decoded.
- Normal workflow: open FM27 → Load Game once → browse career. Diagnostics and discovery tools belong in developer settings, not the primary toolbar.

## Data integrity rules
- Read-only process access (`PROCESS_QUERY_INFORMATION | PROCESS_VM_READ`) remains mandatory. No process write handle, memory patch, save-file write or automatic edit feature is introduced by this importer.
- Keep unknowns null/Unknown. Never infer CA/PA, contract, nationality, team, staff role or generated-player status.
- Regen classification cannot use an age threshold; newgens may be older than real players in long-running saves. UID ranges alone are insufficient. Require a definitive flag or a multi-signal classifier validated against known real/generated examples across different save ages. Until then show Unknown.
- Keep source module hash, game version, object UID, field offset, decode method, witness and confidence for every imported field.
- Preserve `%LOCALAPPDATA%\\FmAtlas\\scouting.db`; migrations must be additive and transactional.
- Do not label the application “FMRTE parity” until every claimed domain is imported and validated.

## Current R4.3 implementation status (truthful)
- One-click live player/club import: implemented and previously tested on the user's Windows build (40,292 named players; 28,497 club records in the reported run).
- Player → team → club relationship: implemented for imported player records and previously witness-tested.
- DOB/age: imported where decoded; age is calculated against the chosen reference date.
- Report-based CA/PA/attributes: implemented for matched players when an external intelligence report has been imported; not a complete all-player live reader.
- Club list and club-linked player view: implemented, but only identity and player links are currently populated.
- Manager identity/My Club: not yet integrated into the production import.
- Staff bulk import: not yet implemented.
- Team hierarchy / reserve / youth squads: not yet implemented.
- Contracts, club finance, competition, season stats, affiliations: not yet implemented as validated bulk import.
- Regen detection: Unknown only; classifier not implemented.
- Windows WPF build: must be run on Windows with .NET 8; this Linux environment cannot compile WPF. No build success is claimed here.

## Genie Scout 27 feature research — additional product benchmark
Genie Scout's current FM27 feature pages describe three main save-wide directories (players, staff and clubs), search-as-you-type, player ribbon filters, attribute-range searches including hidden attributes and mental traits, saved searches, role ratings, current/peak ratings, comparison and similar-player scoring, shortlist import/export, player history snapshots, nine coaching categories, club finance/facility values, and custom/persisted column layouts. Its paid `g` feature set adds role/duty search, potential-attribute search, Find Similar, probability/progress models, top-player lists, cross-save historical GS Stats and an in-game overlay. Genie Scout states that it reads the running game and does not write to the save.

Sources:
- https://geniescout.com/features/
- https://geniescout.com/
- https://www.fmscout.com/a-genie-scout-27g-edition.html

FM Atlas feature translation (own implementation):
- Persisted grid layouts and per-column sort/visibility/width/order.
- Player ribbon filters and advanced attribute ranges; separate player/staff/club query models.
- Position/role ratings only after the official FM role weights and all required attributes/position suitability are mapped and validated. Label FM Atlas's own rating formula and version; never present it as Sports Interactive's internal value unless proven.
- Similar-player ranking with explainable weighted attribute distance and position/role fit; show the weights and confidence.
- History snapshots stored locally from repeated read-only career imports; no claims about other saves unless a separate verified dataset exists.
- Potential-development probability/progress are estimates, not direct FM facts. Do not ship them until calibrated and labelled as FM Atlas model outputs.
- Shortlist import/export should use a documented, tested FM-compatible format and preserve player UIDs; test round-trip before calling it compatible.
- Staff and club pages should be first-class, not secondary pop-ups.

## Build / QA gate for the next integrated release
A release candidate is not complete until all of the following pass on the user's Windows FM27 installation:
1. `dotnet build .\\FmAtlas.sln -c Release` succeeds with zero errors.
2. Existing SQLite DB opens and migrates without deletion or loss of shortlist/player intelligence data.
3. Load Game rejects unknown module hashes and does not write to FM process memory.
4. Manager name, nationality, DOB and employer club match the visible in-game manager profile.
5. My Club opens the exact club resolved from the manager contract.
6. Club directory includes every valid club; every imported player is assigned to the correct club/team or explicitly unresolved.
7. Reserve/youth teams are not conflated with senior team; squad categories match in-game lists.
8. Staff directory has verified identity/employer/job/attributes and counts reconcile with array scan.
9. Contract, finance, player attributes and history values match multiple in-game witnesses, including player-coaches and non-major clubs.
10. Regen classifier is validated against real and generated players from early and long-running saves; otherwise the UI remains Unknown.
11. Search filters, custom columns, sort persistence, comparison, shortlist export/import and club squad drill-down have automated or repeatable UI tests.
12. The UI contains no dead-end controls; discovery/diagnostic tools are tucked into developer settings.
