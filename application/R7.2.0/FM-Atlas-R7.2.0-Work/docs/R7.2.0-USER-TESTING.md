# FM Atlas V10 — First Controlled Windows and FM27 Test Plan

**Purpose:** the first real-world acceptance round for the V10 pre-testing build. This plan is deliberately read-only. It validates startup, existing workspaces, save import, FM27 Data Hub/League Hub evidence and search behaviour before any live editor work is considered.

## Automated baseline already achieved

The pre-follow-up V10 Windows workflow on 14 November 2026 completed successfully:

- .NET 8 solution restore and Release build succeeded.
- Python 3.12.10 installed and verified `fmsave 0.12.4`.
- Save-bridge Python syntax and both Python adapter unit tests passed.
- All 106 xUnit tests passed.
- Self-contained Windows x64 publish completed and the artifact upload succeeded.

The subsequent source hardening adds three regression tests for the V10 live-write gate and fixes the non-blocking dispatcher warning. Use the **latest successful** V10 Windows workflow on `feature/v9-all-roadmap`, not an older artifact. The automated workflow proves build and automated test behaviour; it does not prove that the WPF application has launched on your PC or that imported values match an FM27 in-game screen.

## Before testing

1. Keep all previous FM Atlas folders, ZIPs and source copies unchanged.
2. Download the `FM-Atlas-V10-win-x64` artifact from the latest successful V10 Windows workflow and extract it into a new folder.
3. The published package is self-contained; the .NET 8 runtime/SDK is not required just to launch the published `FmAtlas.exe`.
4. Back up the complete `%LOCALAPPDATA%\FmAtlas` folder before first launch. Do not delete the existing SQLite database, settings or prior snapshots.
5. Create a NEW COPY of an FM27 offline single-player career. Keep the original save untouched. Do not use an online/shared career.
6. Record Windows version, display scaling, FM27 store (Steam/Game Pass), exact FM27 build shown in game and the FM Atlas artifact/workflow run used.
7. Do not upload the career save, personal database, facepacks, logos, passwords or account details when reporting a problem.

## V10 safety boundary — do not bypass

- The V10 pre-testing build is read-only with respect to the FM process.
- Live-memory Apply and Undo are hard-disabled inside the service, even if a supported FM27 process/profile is detected.
- Do not attempt live Apply, live Undo, memory patches or manual toggles.
- Local Atlas-only editing is separate from the FM process. Leave all editing controls alone during this first round; we first need a clean read-only baseline.
- If Tester & Logs does not explicitly report **Live-memory write gate: DISABLED**, stop and report the result before using any FM connection feature.

## Test sequence

### A. Launch and preservation

- [ ] Launch `FmAtlas.exe` from the freshly extracted V10 folder.
- [ ] Confirm the application opens without an unhandled exception.
- [ ] Confirm the Monolith Glass shell, Dashboard and main navigation render.
- [ ] Close and relaunch once; confirm the application starts again.
- [ ] Confirm your existing `%LOCALAPPDATA%\FmAtlas` backup remains intact and no old database was replaced.
- [ ] Open Tester & Logs. Record each check, especially database, log folder, Python/fmsave bridge, FM process detection, store/build profile detection and the hard-disabled live-memory write gate.
- [ ] Check that the support ZIP/report excludes the career save and SQLite database by default.

### B. Navigation and preserved product features

- [ ] Open Home/Dashboard, Players, Staff and Clubs.
- [ ] Open Global Search with Ctrl+K and find a known player.
- [ ] Open Advanced Search and run a query with at least five simultaneous criteria. Check that missing fields remain missing, not zero.
- [ ] Open a player profile and inspect attributes, position ratings and source/evidence labels.
- [ ] Compare at least two players side by side. Check the attribute radar and position-rating comparison; unavailable categories must remain unrated rather than being plotted as zero.
- [ ] Open Similar Players, Value Finder, Scouting Matrix, Tactical Lab/Role Fit, Player Development and Shortlists. Confirm each workspace opens and its basic controls respond.
- [ ] From Scouting Matrix, inspect the shortlist handoff without making unrelated edits. Confirm source metric, period and minutes evidence remain visible.
- [ ] Test search reset/clear, sorting, paging, saved profiles and export only where the displayed control is present.

### C. Import a copied FM27 career through the save bridge

- [ ] Confirm Tester & Logs detects Python 3.12 and `fmsave 0.12.4`. If unavailable, use the included `Setup-FMAtlas-Save-Bridge.ps1` and rerun the check.
- [ ] Use the FMSave Bridge with a COPY of the FM27 career. The reader is intended to be read-only; never point the importer at your only save.
- [ ] Import the generated Atlas snapshot and record the import summary, game/build identity, table counts, warnings and coverage.
- [ ] Confirm the imported player, staff and club totals are plausible for that save; a count alone is not proof of complete field coverage.
- [ ] Open several known player records. Compare player UID, name, club, age, CA/PA and a small set of visible attributes with the in-game FM27 UI where those fields are available.
- [ ] Record every mismatch with the field key, player UID, exact in-game value, Atlas value, FM27 build and source table. Do not infer that an unfamiliar field is an Atlas bug until its source meaning is checked.

### D. FM27 Data Hub and League Hub validation

- [ ] Open FM Player Stats Explorer and confirm the metric catalogue is discovered from rows actually present in the imported save.
- [ ] Test player-season metrics shown in the FM27 Data Hub, such as minutes, goals, xG, passes or tackles, but only where the field is present in the import.
- [ ] Compare the same player, competition and season in Atlas and FM27. Record the exact source table and raw field key.
- [ ] Check per-90 output only where recorded minutes are present. Missing minutes must not be estimated.
- [ ] Open FM League Explorer. Compare a populated standings row with the in-game League Hub/competition screen. If no table row exists in the save, Atlas should show unavailable/empty context rather than inventing a zero-point table.
- [ ] Open FM Team Match Explorer. Check a known retained match report and whether its fixture join is exact. Unmatched reports should remain visible and clearly marked as unmatched.
- [ ] Confirm blank competition/team display names remain blank unless the source or a verified mapping supplies them.

### E. Scouting analytics and optional external data

- [ ] Confirm FM-native statistics remain separate from external provider datasets.
- [ ] If you have a Wyscout player-season CSV that you are entitled to use, import it and check source headers, units, minutes and per-90 fields. This is a CSV adapter, not a Wyscout API or event-feed connection.
- [ ] If you choose to test StatsBomb, use a local copy of the public Open Data folder and compare a few imported match/player event counts with the raw files. This is optional for the first FM27 save check.
- [ ] Do not expect Wyscout event feeds, proprietary provider scores, physical tracking, VAEP or unimplemented event metrics to appear from FM save totals.

### F. Monolith, DPI and stability

- [ ] Check the app at 100%, 125% and 150% Windows display scaling where available.
- [ ] Resize the window and inspect tables, side navigation, filters, profiles and charts for clipping or unreadable text.
- [ ] Leave the app open during a normal search/import session. Note freezes, unusually slow queries, blank pages or unexpected process exits.
- [ ] If testing the live read-only connection, load only the copied offline career and confirm the detected store/build and manager/club identity. An unsupported or ambiguous profile must remain blocked; do not force attachment.
- [ ] Switch to a second copied career only if the first read-only connection is stable. Confirm old and new career facts are not mixed.

## Report back

Use `TEST-REPORT-TEMPLATE.md` and include:

- Exact V10 workflow run/artifact and Windows version.
- FM27 store and in-game build.
- Which section and checkbox failed.
- Expected result versus actual result, exact error and a screenshot.
- For a data mismatch: field key, player UID, in-game value, Atlas value, competition/season and source table.
- A redacted Tester & Logs support ZIP if useful. Do not send the full save or the SQLite database.

## Explicitly out of scope for this first round

Live-memory Apply/Undo, hidden-field writes, personality/position writes, staff/club/contract/transfer/loan edits, installer upgrade/uninstall, database rollback after a write, and any claim of release readiness. Those remain separate future gates after read-only data witnesses and UI acceptance are complete.
