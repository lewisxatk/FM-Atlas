## Executive summary

The recovered FM Atlas R7.2.0 application is a real WPF/.NET 8 desktop application with a substantial SQLite-backed data layer, local save snapshots, read-only live identity acquisition, scouting/search features, limited local editing, a guarded live-memory code path, graphics-pack resolution and a Diagnostics/support-export workflow.

It is not yet the complete integrated Football Manager platform described in the wider roadmap. The navigation contains 21 destinations, but several are shared, narrow or explicitly informational implementations rather than finished standalone products. The largest architectural constraint is a large dynamic WPF code-behind shell and a central SQLite class that combines many persistence, import, search and query responsibilities.

## Stage 1 — reliability and Diagnostics privacy

### What the code actually does

The Tester & Logs route provides:
- Local database and workspace metric checks.
- Local rolling-log storage write check.
- A built-in redaction self-check.
- Python/fmsave version check.
- Football Manager process detection.
- Imported career snapshot check.
- Field-evidence registry summary.
- Exact module-profile detection and an explicit live-write safety warning.
- Copy diagnostics, copy recent log and local support ZIP export.

The support exporter currently builds a fixed in-memory allowlist: `support-report.txt`, `README.txt`, up to five redacted application log files and `manifest.json`. The manifest records file sizes and SHA-256 hashes for the report/README/log entries. The archive is previewed before a Save File dialog. It is written to a temporary file and moved into place after archive creation. No upload or automatic transmission exists in the inspected code.

The support ZIP does not intentionally include career saves, the SQLite database, FM installation files or arbitrary user files. The composition logic has now been extracted into `Services/SupportBundleComposer.cs`, which accepts only diagnostic report text and a strict set of named log entries; it rejects arbitrary filenames and path traversal. The UI uses this composer to create the preview and ZIP bytes.

### Privacy defect found and corrected in source

The Diagnostics checkbox previously promised that opt-in personal details included player names, edit history, the save filename and local database path. However, the report was passed through the final redaction pipeline, which deliberately removes absolute paths and standalone Football Manager save filenames even when the checkbox was selected. The UI/README therefore over-promised what the export would contain.

The source has now been corrected so the opt-in is limited to player names and recent edit history. Absolute paths and career save filenames are explicitly always redacted. The report uses a standardised LocalAppData placeholder, the README and preview state the same policy, and the manifest has an `alwaysRedacted` declaration for credentials/tokens, absolute paths and career save filenames.

This is a privacy-preserving correction, not permission to include more personal information. Five new `SupportBundleComposerTests` exercise the ZIP allowlist, archive round-trip, manifest hashes/sizes, redaction and path-traversal rejection. Their Windows run is pending; manual inspection of a real ZIP generated by the Windows app remains outstanding.

### Redaction cases currently covered

- Bearer tokens and Basic authorization credentials.
- API keys, access/refresh tokens, client/private secrets and passwords.
- Quoted JSON/config secrets, including values with spaces.
- URL query-string access tokens.
- Drive-letter paths with spaces and UNC paths.
- Standalone .fm/.fmf/.dat filenames.
- Line-break flattening and output length cap.

### Remaining Stage 1 acceptance

1. Pass Windows build/tests for the corrected privacy wording and manifest.
2. Launch the app on Windows and run Tester & Logs.
3. Generate both default and personal-details-opt-in ZIPs using test/demo data.
4. Open each ZIP independently and compare actual entries with the preview and manifest.
5. Recalculate SHA-256 hashes and verify every listed file.
6. Confirm no career save, SQLite database, arbitrary file, absolute path, save filename or credential appears.
7. Test cancel before save, overwrite prompt, write failure/temp-file cleanup and a large/rotated log set.
8. Verify the checkbox changes only the explicitly disclosed player-name/edit-history fields.
9. Check that failures in a diagnostic check do not cause sensitive exception details to leak into the log/export.

No manual ZIP inspection is claimed yet.

## Stage 2 — source architecture and route-by-route audit

### Observed application architecture

- C# WPF application targeting `net8.0-windows`.
- Dynamic UI is built largely in `MainWindow.xaml.cs` rather than separated into a mature MVVM/component architecture.
- The main shell owns sidebar navigation, active page state, page loading, keyboard shortcuts and route dispatch.
- The inspected MainWindow source is approximately 1,980 lines in the source revision described by the existing architecture audit.
- `Data/ScoutDatabase.cs` is approximately 2,665 lines in the audited revision and centralises SQLite schema, imports, queries, metrics, facts, shortlists and edit-history operations.
- Feature-specific partials exist for Advanced Search, Diagnostics, R7 analytics/mass edit, Role Lab and Value Finder.
- The active source tree now contains 41 application source files and 11 test-project files (including the test project file). This is a compact monolith, not yet a modular application platform.

### High-value reverse-engineering findings

#### 1. Save parsing and offline data

- Atlas uses a local Python Launcher adapter for `fmsave 0.12.3`.
- The bridge runs the parser against a selected save and writes JSON under the user's LocalAppData Atlas imports folder before importing it into SQLite.
- The UI describes the source save as read-only; no direct save-file write path was identified in this bridge.
- Version/layout validation is important: a recognised parser layout does not prove that every field meaning is correct for every FM27 build.
- Raw/unknown data and validation warnings should be preserved; missing fields must not become fabricated zeros.

#### 2. Live memory and safety

- The live adapter looks for the `fm` process and `game_plugin.dll`, then matches registered PE image size and timestamp profiles.
- The registry contains separate Game Pass and Steam profiles, including older Launch Preview profiles.
- The code has staged changes, field whitelisting, player UID/name re-resolution, current-value preflight, save-load generation checks, per-field checks, read-back and undo/rollback logic.
- A module fingerprint is only a profile selector, not proof that every field offset or meaning is correct.
- `LiveWriteCertification.IsCertified` currently returns false; Apply and Undo are blocked. Keep this gate closed until the exact user's Game Pass build and field mappings are independently witnessed and disposable-save Apply/read-back/Undo acceptance is complete.

#### 3. Evidence and identity

- Field evidence distinguishes Unverified, Candidate, ProfileMatchedProvisional and FieldVerified.
- Exact canonical status matching replaced substring checks that could accidentally treat the word `Unverified` as verified.
- Cross-provider player IDs are not merged by name similarity. Exact source IDs can be deduplicated; cross-provider identity requires a verified crosswalk.
- This conservative approach avoids false identity merges and false claims of field certainty.

#### 4. Role and performance intelligence

- RoleFitService contains 23 explainable coaching-style profiles with explicit Atlas weights.
- Valid attribute inputs are finite 1–20 values; at least half of requested attributes must be present; missing values are not treated as zero.
- Per-player additive contribution terms are surfaced in Role Lab and tested through a SQLite query integration.
- These weights are Atlas's model, not Football Manager's internal formula or star rating.
- Metric calculations and search conditions have unit tests, but full metric coverage and cohort normalisation remain dependent on trustworthy imported source data.

#### 5. Search and assistant limitations

- Global Search currently covers Players, Staff and Clubs, with filters and result grids; it is not yet the planned Ctrl+K command palette.
- Attribute Search is narrow AND criteria; Stats Search has ALL/ANY semantics for a single player-period row.
- The Assistant is a small rule-based parser and explicitly reports its limited applied filters.
- Saved profiles, nested Boolean groups, richer entity search, query explanations and a universal field registry remain incomplete.

#### 6. Graphics and modding

- GraphicsResolver reads existing `config.xml` mappings and indexes image files inside the selected graphics tree; it does not bundle or duplicate graphics packs.
- It discovers common Documents/OneDrive paths or uses an explicitly selected config.xml.
- Path containment checks and avoidance of directory reparse points are present in the inspected resolver.
- The user's actual Game Pass graphics root, pack precedence, large-library performance, FaceDrop separation and cache invalidation have not been tested on the user's PC.
- Skin/mod installer workflows are not present as a complete product area.

#### 7. External tool research and licensing

The existing research register identifies useful architectural references:
- `fmsave`: offline save parser, stated MIT licence.
- `fm-editor`: live-memory editor, stated GPL-3.0-or-later.
- `FMLibreEditor`: FM27 Game Pass/Steam live editor, stated GPL-3.0-or-later.
- `FMSuperScout`: scouting scanner/core and snapshot model, stated MIT licence.
- `gilet`: save-container format investigation.
- `FMM Editor`: pre-game database editing concepts, not a substitute for live-save editing.

These are research references, not dependencies. Do not copy or link GPL code into a distributed Atlas build without a deliberate licence decision. Continue independent implementation from documented behaviour and verified interfaces. Project README claims and performance claims are not independently proven by Atlas.

## Architectural conclusions and recommended direction for the later combined build

These are recommendations for the user's later Stage 3–7 approval, not work being started now:

1. Establish a canonical field/entity registry and provenance contract before expanding search, analytics or editing.
2. Split UI page composition from application services and database operations; keep the existing working behaviours as regression fixtures.
3. Build shared MONOLITH design tokens and reusable WPF components, then migrate all routes consistently.
4. Consolidate search criteria into a typed query model with explicit AND/OR groups, missing-value semantics and saved profiles.
5. Integrate Role Lab, Squad Architect and Tactical Lab only when the underlying role/position/tactic inputs have validated provenance.
6. Keep transfers, valuation and cross-league comparisons honest about missing fees, wages, asking prices, cohorts and calibration.
7. Keep live-memory Apply/Undo disabled until build- and field-level certification plus disposable-save verification are complete.
8. Treat Game Pass process integration, save import and graphics discovery as separate adapters with explicit compatibility evidence.
